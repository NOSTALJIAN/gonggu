# 기존 v25 RPC를 사용하는 배송이력 표시

현재 프런트엔드는 **이미 존재하는 v25 조회 함수만 사용**합니다. 새 v26 SQL 설치, Supabase 권한·테이블 변경, Apps Script 변경은 수행하지 않았습니다. 기존 주문·가격·결제·묶음 설정·배송완료 처리도 유지합니다. 이전 03 SQL과 관련 감사/DB fixture는 과거 검토 자료이며 이번 구현에 설치할 필요가 없습니다.

## 실제 호출과 확인 범위

- 구매자: `gq_lotte_tracking_for_quote_v25(p_quote_id, p_lookup_token)`
- 관리자: `gq_lotte_tracking_admin_v25()` (본문 `{}`, 기존 관리자 JWT 사용)
- 기존 `gq_read_quote`와 `gq_is_admin` 인증 흐름 유지
- v26 RPC fallback, private 테이블 직접 읽기, 부모 주문/다른 토큰 탐색 없음

공개된 기존 publishable key로 읽기 전용 함수 호출을 확인했습니다. 키·토큰 값은 로그에 출력하지 않았습니다.

| 실제 확인한 요청 | 결과 | 확인 범위 |
|---|---|---|
| 존재하지 않는 견적/토큰으로 구매자 RPC | HTTP 200, JSON null | 공개키 역할에서 호출 가능, 이 입력은 배송정보를 반환하지 않음 |
| 비로그인 관리자 RPC | HTTP 401, code 42501, 함수 실행 권한 거부 | 비로그인 호출 차단 |
| 공개키로 OpenAPI | HTTP 401 | 현재 키로 성공 응답 스키마를 조회할 수 없음 |

이 환경에는 유효한 구매자 토큰/관리자 로그인 정보가 없습니다. **실제 성공 응답 및 운영 10건 표시를 확인한 것으로 보고하지 않습니다.** 새 관리자/서비스 키를 요청하거나 기존 권한을 넓히지 않았습니다.

## 응답 변환: 알려진 구조와 아직 미확정인 키

사용자가 확인한 바깥 구조는 구매자 JSON 객체 또는 NULL, 관리자 송장번호를 키로 한 JSON 객체입니다. JSON 내부 키는 마스킹되어 정확한 이름이 아직 미확정입니다.

변환기는 다음과 같이 **식별 가능한 레코드에 한해서** 처리합니다. 아래는 지원하는 레코드 필드이며, 운영 RPC의 성공 응답이 이와 같다고 확정한 예시는 아닙니다.

| 인식 가능한 필드 | 화면에서 사용하는 값 |
|---|---|
| tracking_number | 정규화한 송장 식별자 |
| events 배열 | 저장 이벤트 전체 및 원래 순서 |
| events[].time | 원본 시각 문자열·시간대 유지 |
| events[].place 문자열 또는 name/text 객체 | 위치 |
| events[].status + 서로 다른 detail | 처리상태·상세 |
| status_label / status_code | 실제 조회 상태·코드 |
| event_time / checked_at | 실제 이벤트/조회 시각 |

구매자는 응답의 tracking_number가 자신의 기존 주문 송장과 일치해야 합니다. tracking_number 누락, 다른 송장, NULL, 배열/알 수 없는 중첩 envelope 등은 이력으로 표시하지 않습니다. 관리자 응답은 서버가 제공한 송장 맵 키를 식별자로 사용할 수 있지만, 레코드에 별도 tracking_number가 있으면 키와 일치해야 합니다. 같은 송장으로 정규화되는 여러 키가 서로 다른 결과·불완전한 결과를 제공하면 임의 선택 없이 해당 송장 이력을 보류합니다.

필드가 없거나 형식이 다르면 재귀 탐색으로 다른 주문 데이터를 찾아 맞추지 않습니다. 실제 저장 이력이 없는 경우 테스트/체험 이력을 대신 만들지 않습니다. 원래 주문의 택배사·송장·상태·금액도 배송 응답으로 덮어쓰지 않습니다. 렌더링할 때 모든 값은 HTML escape합니다.

## 하이픈과 묶음배송

공백·하이픈을 제거한 송장으로 레코드 매칭, 관리자 묶음 송장 비교, 공식 조회 URL을 만듭니다. 저장된 원래 송장 및 배송상태는 변경하지 않습니다. 관리자에게 로드된 승인 묶음은 대표 송장만 있어도 같은 이력을 공유 표시합니다. 일부가 먼저 배송완료여도 카드 묶음 기준은 유지합니다.

**서버 내부 조회의 정규화는 별도 확인 대상입니다.** v25 RPC가 주문 송장을 원문 그대로 DB와 비교한다면, 하이픈 있는 주문이 서버에서 NULL을 받는 문제는 프런트엔드 매칭만으로 고칠 수 없습니다. 실제 하이픈 유무 각각의 정상 주문으로 확인해야 합니다. 그런 실패가 확인될 때만 기존 v25 조회 WHERE 조건의 정규화 보완을 별도 제안하며, 이번 작업에서는 SQL을 생성/적용하지 않습니다.

## 구매자에게 송장이 없는 추가 주문

본인 주문에 송장이 없으면 부모 주문이나 관리자 응답을 임의로 가져오지 않고, 화면에 운영자에게 송장 등록 상태를 확인하라는 안내를 표시합니다. 관리자 상태/캐시가 브라우저에 남아 있어도 구매자 페이지는 이를 이력 상속에 사용하지 않습니다.

안전한 해결 방법은 기존 관리자 승인 흐름이 지원하는 범위에서 동일 송장을 각 주문에 등록·동기화하는 것입니다. 실제 작업 전 완료된 주문의 상태를 되돌리지 않는지 기존 기능을 확인해야 합니다. 이번 구현은 자동 동기화나 송장 쓰기 요청을 보내지 않습니다. 기존 구매자 v25 RPC의 서버 측 승인된 상속 지원이 따로 확인되면 해당 응답을 정확한 계약에 맞춰 연결할 수 있습니다. 그 필요가 확인되기 전에는 신규 v26 설치를 제안하지 않습니다.

## 테스트와 남은 실제 확인

- `node --test tests/shipping.cjs`: 응답 변환, 송장 불일치/모호성 차단, 캐시 격리, 기존 필드 보존, JavaScript 구문 검사
- `node tests/shipping-browser.cjs`: 외부 요청을 전부 차단한 fixture로 v25 인자/권한 헤더, 관리자 맵·구매자 레코드, 10개 이력 행, 시간/place/status/detail, 혼합 상태 묶음 카드, NULL/누락/권한 오류, 다른 송장/미확인 형식 차단 확인

테스트 JSON은 명시적인 테스트 데이터이며 운영 성공 응답을 확인한 자료가 아닙니다. 운영에서 확인할 것은 (1) 성공 응답의 실제 내부 키, (2) 유효한 관리자·구매자 조회에서 실제 저장 10건 표시, (3) 하이픈 송장의 서버 조회, (4) 송장 없는 자식 주문에서 v25가 제공하는 범위입니다. 필드명이 다르면 실제 성공 응답의 민감한 값을 가린 구조에 맞춰 변환기만 조정하면 됩니다.

GitHub 반영 준비 파일은 index.html, tests/shipping.cjs, tests/shipping-browser.cjs, 이 문서입니다. 기존 SQL 검토 파일은 이번 배포의 필수 항목이 아닙니다. 프런트엔드 배포에 Supabase SQL이나 함수 변경은 포함하지 않습니다.
